When you're building a meeting scheduling platform, the time-slot generation algorithm is the heart of the system. Every user action — picking a date, changing a timezone, adding a guest — triggers it. For a long time, ours worked fine. Then it didn't.

This is the story of how I found the bottleneck, fixed it, and cut scheduling load time by 30%.

## The Context

We were building a SaaS scheduling platform integrating with Google Calendar, Outlook, and Apple Calendar. The core feature: given a host's availability rules and a set of guests, find all possible meeting slots in a given window.

The API endpoint looked straightforward:

```python
@router.get("/slots")
async def get_available_slots(
    host_id: str,
    duration: int,          # meeting length in minutes
    window_start: datetime,
    window_end: datetime,
    guest_ids: list[str],
) -> list[TimeSlot]:
    ...
```

Simple enough. But as users set longer look-ahead windows — 4, 6, 8 weeks — response times crept up. P95 latency crossed 3 seconds. That's a dead UX.

## The Original Approach

The original algorithm was intuitive but naive:

1. Fetch all calendar events for the host and every guest in the window
2. Merge them into a single sorted list of "busy" periods
3. Walk the window minute-by-minute, checking if `[t, t + duration]` is free for everyone
4. Collect all valid slots

Step 3 was the killer. For an 8-week window with a 30-minute slot duration:

```
8 weeks × 7 days × 16 hours × 2 checks/hour = 1,792 iterations
```

Each iteration performed a linear scan against the busy-period list. With 5 guests each having ~40 events per week, that list had ~1,600 entries. The nested loop complexity was effectively **O(W × E)** — window size times total events.

It worked in demos. It didn't work in production.

## Finding the Bottleneck

Before rewriting anything, I profiled. This is the most important step — optimise what's actually slow, not what feels slow.

```python
import cProfile
import pstats

profiler = cProfile.Profile()
profiler.enable()
slots = get_available_slots(...)
profiler.disable()

stats = pstats.Stats(profiler)
stats.sort_stats("cumulative")
stats.print_stats(10)
```

The output was unambiguous: 94% of time was in `_is_slot_free()` — the function checking a candidate slot against the busy list. Specifically, the inner loop iterating over every busy period for every candidate time.

## The Fix: Sweep Line + Interval Merging

Instead of checking each minute against every event, I switched to a **sweep line approach**:

1. Collect all busy intervals across all participants
2. **Merge overlapping intervals** into a single consolidated list
3. Walk the **gaps between merged intervals** rather than every minute

```python
def merge_intervals(intervals: list[tuple[datetime, datetime]]) -> list[tuple[datetime, datetime]]:
    if not intervals:
        return []

    sorted_intervals = sorted(intervals, key=lambda x: x[0])
    merged = [sorted_intervals[0]]

    for start, end in sorted_intervals[1:]:
        last_start, last_end = merged[-1]
        if start <= last_end:
            merged[-1] = (last_start, max(last_end, end))
        else:
            merged.append((start, end))

    return merged


def get_free_slots(
    window_start: datetime,
    window_end: datetime,
    busy: list[tuple[datetime, datetime]],
    duration: timedelta,
) -> list[tuple[datetime, datetime]]:
    merged_busy = merge_intervals(busy)
    free_slots = []

    cursor = window_start
    for busy_start, busy_end in merged_busy:
        # The gap before this busy period
        while cursor + duration <= busy_start:
            free_slots.append((cursor, cursor + duration))
            cursor += duration
        cursor = max(cursor, busy_end)

    # Remaining time after all busy periods
    while cursor + duration <= window_end:
        free_slots.append((cursor, cursor + duration))
        cursor += duration

    return free_slots
```

The complexity dropped from **O(W × E)** to **O(E log E + S)** — where S is the number of valid slots (much smaller than W). The `log E` comes from the sort; finding slots is now a single linear pass over the merged intervals.

## The Results

After deploying the new algorithm:

| Metric | Before | After |
|---|---|---|
| P50 latency | 1.1s | 0.7s |
| P95 latency | 3.2s | 2.1s |
| P99 latency | 5.8s | 3.9s |
| **Avg load time** | **~1.4s** | **~0.98s** |

A **30% reduction in average scheduling load time** across all window sizes. For 8-week windows, the improvement was closer to 55%.

## What Made the Difference

Three things, in order of impact:

**1. Profile before you optimise.** I had a hunch the event fetching was slow (network calls, async overhead). The profiler said it wasn't. Never trust hunches over data.

**2. Change the algorithm, not the implementation.** Rewriting the inner loop in a more Pythonic style, caching results, adding `functools.lru_cache` — none of that would have moved the needle meaningfully. The O-complexity was the problem.

**3. Merge first, walk second.** The core insight is that users don't care about individual events — they care about consolidated free time. Merging busy intervals early is cheap and transforms a hard problem into a simple one.

## Takeaway

Performance problems in scheduling systems usually aren't database or network issues — they're algorithmic. If you're building anything that computes availability across multiple calendars, start with interval merging. It's one of those patterns that looks like extra work upfront and saves you significant pain later.

If you're dealing with similar problems, the [ICal.js](https://github.com/kewisch/ical.js) library (for JS) or the `recurring_ical_events` package (Python) are worth looking at for handling recurrence rules — the next complexity layer I had to tackle.
